# Veera — Fix

Explicit `/veera:fix <task>` remains optional. Continue in the same turn without asking the user for an activation command, separate start message or routine confirmation. Automatic entry does not enroll, expand scope or authorize publication. An inspection-only request does not authorize edits or publication.

**Mode.** For a new automatically routed task, freeze `delivery_mode: "local-verify"` unless the user requested publication; preserve the mode of an existing task; never change an initialized task to another mode. For an explicitly nonpublishing task, freeze `delivery_mode: "local-verify"` and omit `release` before init. In that mode the release/version requirements below do not apply: prohibit release-prepare/reconcile/publish, retain every scope/behavior/count/fingerprint/review/blocker/ownership gate, and finish to terminal `verified-local`. Report "verified locally; unpublished" and preserve the worktree/evidence; never claim published complete/DONE or automatically archive the task.

**Read.** `${CLAUDE_PLUGIN_ROOT}/docs/agent-contract.md`: Operating core first, then Authority and ownership, Session isolation, Bounded contract, Runtime interface, and Evidence and immutable DONE; UI acceptance for UI defects; Selective reasoning, context and repair before delegation or repair. `${CLAUDE_PLUGIN_ROOT}/docs/engineering-standards.md`: Applicability and authority, Role routing, Verification and evidence, then the sections the defect touches, before lock. Native/project instructions, permissions and stricter recovery ceilings remain binding.

**Own the outcome.** Own diagnosis through the complete authorized fix: tests, independent review, patch version and release. Never voluntarily stop at a partial fix or a soft target or pause for routine approval; report real blockers, never fabricated completion. No recursive delegation, nested loops, schedulers, automatic workflows or permission bypasses. Use medium effort only if supported by the host; otherwise inherit its setting without claiming a change; never force max or another model. Cut redundant context, never verification or causal reasoning: read each source once, cite rule and criterion IDs instead of re-reading, never rerun an unchanged command. Return concise evidence and rationale, not chain-of-thought.

## Fix method

A change without a reproduced failure is a guess; a claim without a recorded result is not evidence.

1. **Baseline once.** Run the project's existing test command once and keep its counts and failures under `.veera-artifacts/`. A green suite shows only what the tests cover; it does not clear the defect.
2. **Inventory defects.** Start from reported failures or symptoms. When no failure list is given, the specification and project documentation are the oracle: read them once into a numbered rule table (inputs and validation, status/error codes, limits, ordering, authorization and tenancy, concurrency, idempotency, time and expiry, pagination, persistence, audit), noting for each rule the enforcing code and the covering test. An uncovered rule or code that disagrees with the text is a suspect. Comments, names and markers are leads, not evidence. The specification bounds the search; this is not a code-quality audit.
3. **Reproduce.** Probe each suspect with the smallest executable check in the project's own test idiom against unchanged source. Before init draft probes only under `.veera-artifacts/probes/`, run them together in one host-approved invocation and keep the output; probe runs must not write elsewhere in TASK. A probe failing on the rule's violation confirms a defect; a passing probe clears the suspect.
4. **Root cause.** Trace each confirmed failure backward to where the wrong value, state or ordering originates and name the violated invariant ("X causes it because evidence Y"). Test one hypothesis at a time; a disproved hypothesis gets a new one, never a stacked edit. Search the same pattern (shared helper, copied handler, same check order) and probe siblings inside the authorized scope. Fix at the source, not the symptom.
5. **Freeze.** Each confirmed defect becomes a criterion (rule ID, expected versus observed, probe output path, impact) with a focused regression check covering its failure states; add the project's full test command as a no-regression check when proportionate. Unconfirmed suspects are reported as hypotheses, not edited.
6. **Red, then green.** In `implement`, move each probe into in-scope test files and run it on the unfixed code: it must fail for the stated reason, not a typo or setup error. Keep that output; when a red run is impractical, say so in the report. Make the smallest root-cause correction, rerun the regression to pass, then the full suite. A miss returns to step 4 with the new evidence. After a hypothesis repeats or three distinct fixes miss the same failure, stop guessing and take the evidence to Advisor/Architect through the Bounded blocker protocol.
7. **Verify once.** Enter `verify` only after every frozen argv already passes in the host shell. A failed controller `check` cannot rerun until `repair` with a new reason, which spends one of the bounded global repairs. A check fails if the run changes the tree ("repository changed during check"): route test output to OS temp or ignored paths outside scope before lock. The count regex must match the runner's own summary; all matches are summed and zero fails.

Detect the stack and follow its idioms/tools; prefer existing trusted facilities over adjacent rewrites, refactors, dependency installs, shared-runtime changes or speculative updates. Apply Repository hygiene and resource ownership: clean only proven task-owned disposable artifacts, stop only exclusively owned activity, preserve evidence/peer work, never manage shared caches/processes or touch other projects/global settings, and include authorized tracked cleanup in the single final verified delivery. For frontend defects apply Frontend craft, central design and accessibility without unrelated redesign: preserve central components/tokens, fix actual interaction/responsive states, verify affected WCAG 2.2 AA criteria from actual references/design-system sources and rendered/browser evidence (unavailable required evidence blocks that gate). Pass specialists section pointers and role deltas. Guidance is not compliance evidence and cannot weaken frozen acceptance or expand repair authority.

## Establish and freeze

Only the coordinator owner runs the CLI. Required forms (quote actual values; placeholders are not IDs or environment variables):

```text
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/delivery.py" doctor
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/delivery.py" workspace --root ORIGINAL --task SLUG --session-id ACTUAL_HOST_ID
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/delivery.py" SUBCOMMAND --root TASK --session-id ACTUAL_HOST_ID --capability-file OWNER_FILE [COMMAND_ARGUMENTS]
```

Every other public root command uses the third form, including all shorthand fragments below. Never delegate the capability or CLI use.

1. **Identity.** Use the successful hook bootstrap from this request or retained actual bootstrap from this same chat. Use only its actual host `session_id` and configured persistent `CLAUDE_PLUGIN_DATA`; missing values block startup. Carry that data directory explicitly into CLI child environments if not inherited, with `VEERA_HOST=claude` (the default). Never invent a session variable, ID or environment fallback, auto-enroll other sessions or adopt legacy unbound runs; migration follows Session isolation (separate authorization, actual old-owner quiescence). Routing reads only `${CLAUDE_PLUGIN_DATA}/veera-v1/claude/sessions/<sha256 session_id>.json`, never enumerates records or falls back to a plugin-local registry. Unbound hooks no-op without cwd/project inspection; bound wrong-cwd/nested-repo calls block. Do not scan/repair unrelated runs when updating the plugin.
2. **Workspace.** Resolve the original authorized Git root and applicable CLAUDE.md/AGENTS.md; require it clean and committed, then run `workspace`. Use the returned canonical TASK root, binding and owner file, never the original checkout, for all task work, including discovery. It creates sibling `veera-SLUG` on `veera/SLUG`; its shared Git metadata and narrow lock grant no authority over shared ignores/config or peers. Before init the bound owner may read only its own task/plugin docs and write only draft `.veera-artifacts/`, never source; arbitrary Bash is ASK for host approval, not a sandbox; global ListAgents enumeration is blocked. On same-bound-task resume use `status --root TASK`; reconcile identity, contract, fingerprint, elapsed time and repairs, not fresh authorization. Never reinit to reset limits; DONE is terminal.
3. **Discover** (Discovery section below and Fix method steps 1–5). Record start time, a task-derived soft target and authorized hard ceiling from the work items and their estimates, including diagnosis, review and release; respect stricter user/project limits. Missing credentials or denial is a blocker, not a bypass opportunity. Resolve ordinary defaults from project evidence; ask only for material missing input or human authority. A soft target requires replanning, not abandoning diagnosis or broadening into an audit.
4. **PM.** The coordinator owns PM responsibility throughout; delegate PM selectively. Material scope/budget decisions and soft-target replans require actual Architect impact analysis and Advisor alternatives before the PM-owned decision. No invented consultation or routine committee. Reserve time for checks, review and release; do not trim required outcomes.
5. **Contract.** Write and read back the Bounded contract under TASK's `.veera-artifacts/`: frozen scope, observable criteria/check IDs, inspected check argv/kind/count regex/timeouts, non-goals, UI references, repair ceiling and `release` (names `origin`, `main`, the single supported version file in scope, and `push_authorized: true` only with user authority). Freeze expected behavior, not merely “tests green”; lock regression checks before remediation. Runtime queries skip only UNTRACKED reserved bookkeeping paths and reject tracked reserved source; raw Git status may show bookkeeping, so never hide it via shared `.git/info/exclude`/config/ignore edits or put source/tests there. Missing authority/repository requirements block complete delivery.
6. **Init.** Run `doctor`, then `init` once with `--mode fix --request TEXT --contract CONTRACT.json --minutes TARGET --hard-minutes HARD_ALLOWANCE`, passing remaining allowances without restarting discovery time. Rejected requirements are blockers; do not invent execution records. Then start the dashboard (Automatic live dashboard below).

## Remediate, prove, deliver

1. `phase --root TASK --name discover`, then `plan`: state causal evidence and the smallest correction. Frozen criteria and commands cannot be weakened to fit an implementation. Phases move one step at a time.
2. Coordinator alone routes triggered specialists. Read `context --root TASK` for the shared brief; every role gets the same run/contract/revision/current-fingerprint identity plus its role delta, criterion IDs, sources, blockers and remaining allowances. Memory updates come from the actual `memory-steward` (read-only, JSON return); the coordinator validates/saves and imports with `context-import --root TASK --file PROPOSAL` under Shared TASK context limits. Checkpoint before compaction; no secrets/full logs/transcripts, parallel store, services or automatic refresh; cache savings are unmeasured. Share only allowed task evidence/narrow permissions with actual spawned roles; no unrelated ListAgents/SendMessage use or all-agent fan-out; host subagent inheritance is unverified, not an auth guarantee.
3. `phase implement`: Fix method step 6 in the task worktree. Check `status` and original elapsed time before costly work. Soft expiry sets a replanning flag, not a stop: obtain actual required consultation, record `decision --root TASK --file DECISION.json` and continue the unchanged outcome under the existing hard ceiling. No token/time shortcut may discard acceptance or evidence.
4. Publishing only: call `release-prepare --root TASK` while still in `implement`, after focused checks pass. It fetches authorized `origin/main`, integrates main only in TASK and idempotently patch-bumps the declared version. Preserve peers, never merge unrelated branches; resolve conflicts only within authority.
5. `phase verify`; run every required `check --root TASK --id ID` on the final tree. Zero tests, static-only/synthetic/stale/missing output and unrelated success do not prove the fix. UI requires actual rendered screenshots and browser interaction evidence.
6. `phase review`; obtain an actual independent project/plugin reviewer against frozen criteria, causal evidence (red and green outputs), prepared source/diff and check/UI output at the same `fingerprint`. No predetermined verdict or self-attestation. Authorize only its review JSON path under `.veera-artifacts/`, read it and import with `review --root TASK --file REVIEW.json` using actual reviewer identity; criteria must equal every criterion ID.
7. A failed check or review follows the Bounded blocker protocol: `blocker --root TASK --file OP` (`open|attempt|result|reconcile|resolve|decision`) keyed by stable family+target, each distinct attempt persisted before action and its result after (at most three per blocker; unchanged attempts are rejected), then `repair --root TASK --reason TEXT` with a new reason before corrective edits; it returns to `implement` and clears review. Global repairs default to three, respecting lower contract/project limits and legacy explicit two. Denial/auth/human-only issues block immediately without retry. At exhaustion: actual Advisor+Architect consultation, then a PM-owned decision (independent reprioritization or at most one bounded alternative route per TASK), never a reset of attempts/global repairs, an override of hard stops or a retry of the exhausted target. Resolve only with evidence; source changes require fresh checks/review.
8. `finish --root TASK` only with all gates current and no unresolved blocker. Local-verify yields `verified-local`. Publishing yields `ready`, not DONE; keep one final remote push intent (no intermediate remote branches/tags, PR/status writes or manual Actions runs; local commits are fine). Then `publish --root TASK` commits the exact verified tree and prefetches to confirm remote main matches the reviewed base before at most one authorized plain non-force push to `origin/main`; no force-with-lease or history overwrite, and a non-fast-forward race rejects. Main checked out anywhere blocks publish BEFORE push; never read/alter that checkout or detach, stash, merge, reset or update-ref peers to unblock it.
9. Successful `publish` (complete) or local `finish` (verified-local) automatically releases only this chat's binding, preserving worktree, state and evidence; that result is the completion receipt. Do not issue another owner status/unbind command after session_binding is released. If cleanup-required is returned, resolve the cleanup issue and retry only unbind, never publication. Failed or ambiguous pushes retain their evidence and prohibit automatic retry. Original/peer checkouts and local main remain unchanged.
10. At hard expiry, user stop, denial, exhausted repairs or a genuine blocker with no eligible work, call `stop --root TASK --reason TEXT` and `checkpoint --root TASK --reason TEXT`; report unresolved criteria, causal uncertainty and exact prerequisites. Use `resume --root TASK --file REPORT.json` only with `checkpoint_id`, actual user approval in `authorization`, `reason` and `additional_minutes` equal to the sum of authorized remaining-task estimates in `time_plan`, respecting stricter limits; require matching fingerprint, preserve repairs/time history and never reinit. Hard expiry requires new explicit human allowance. Other recovery follows `docs/recovery-authorization.md`. No unattended continuation promise.

Return each defect's confirmed cause (or remaining hypothesis) with its rule ID, the scoped correction, red and green regression outputs (or why red was impractical), actual check counts and exits, UI status, reviewer identity, patch version/release and push status, gaps and runtime state. A patch or implementation-ready result is not complete delivery.

## Model selection

Read `docs/model-routing.md` under the resolved package root and apply `docs/model-policy.json` before each bounded work item: Codex Sol for light work, Astra for important work. Select through supported host controls, report unavailable required models, and do not claim this text switches the current model; Claude keeps its selected native model. ## Discovery, initial questions and internal decisions

Before planning, init or source edits, read `docs/requirements-analysis.md` and `docs/intake-and-autonomy.md` under the resolved package root. For an underspecified or consequential request, use the requirements analyst process to inspect relevant code, project/domain documentation and necessary current primary sources, resolve contradictions and turn evidence into observable requirements and an ordered plan; for a precise small change, keep analysis proportionate. Investigate first and reuse existing answers. Conduct all necessary clarification in this initial discovery: offer two or three options with an evidence-based recommendation and tradeoffs, allow a custom answer, follow up here if essential ambiguity remains, and never infer an answer from silence. Show the scope, acceptance and plan, then continue under existing authorization without another approval gate. Freeze validated `contract.discovery` and `contract.intake`, with no essential questions outstanding, before init.

Once implementation starts, PM, Architect and Advisor handle eligible decisions through the coordinator within captured limits. Do not restart preference interviews or ask repeated confirmations. Block only a genuinely human-only/denied/out-of-scope action, preserve its evidence and continue independent eligible work. Internal recommendations never grant native permissions or expand consent.

## Automatic live dashboard

Immediately after successful init and before the first implementation edit, follow `docs/dashboard.md`: launch the owned `dashboard --root TASK --port 0` in a host-tracked background process; it opens the browser and saves the live address. Capture its output/process handle and show the user the actual clickable URL once, never an assumed launch. Do not wait for a request or ask permission for this routine local preview. Reuse an existing task server, never duplicate it; it is not a scheduler or gate. Later requests for the dashboard or its path use `dashboard-info` (validated URL and absolute record path). A browser launch failure falls back to the link while eligible work continues.
