# Veera — Fix

Guidance 0.3.0. Start automatically for an ordinary user request matching this skill. Read `docs/automatic-entry.md` under the installed package root and use the actual host bootstrap context. Explicit `/veera:fix <task>` remains optional. Continue in the same turn without asking the user for an activation command, separate start message or routine confirmation. Automatic entry does not enroll, expand scope or authorize publication. For a new automatically routed task, freeze `delivery_mode: "local-verify"` unless the user requested publication; preserve the mode of an existing task.

## Shared rules

For an explicitly nonpublishing task, freeze `delivery_mode: "local-verify"` and omit `release` before init. In that mode the release/version requirements below do not apply: prohibit release-prepare/reconcile/publish, retain every scope/behavior/count/fingerprint/review/blocker/ownership gate, and finish to terminal `verified-local`. Report "verified locally; unpublished", preserve the worktree/evidence; successful CLI finish releases the binding automatically. Never claim published complete/DONE or automatically archive the task. Select publishing only when the user requested it; never change an initialized task to another mode.

Read `${CLAUDE_PLUGIN_ROOT}/docs/agent-contract.md` sections Authority and ownership, Session isolation, Bounded contract, Runtime interface, and Evidence and immutable DONE. Read UI acceptance for UI defects, and Selective reasoning, context and repair before delegation or repair. Native/project instructions, permissions and stricter recovery ceilings remain binding.

Own diagnosis through the complete authorized fix, including tests, independent review, patch version and release. An inspection-only request does not authorize edits or publication. Never voluntarily stop at a partial fix or a soft target; continue eligible work without routine approval pauses. Report real blockers rather than fabricate completion. No recursive delegation, nested loops, schedulers, automatic workflows or permission bypasses.

Use medium effort only if supported by the host; otherwise inherit its setting without claiming a change. Never force max or another model. Reduce redundant context, not verification quality or careful causal reasoning. Return concise evidence and rationale, not chain-of-thought.

Guidance is not compliance evidence and cannot weaken frozen acceptance or expand repair authority.

## Diagnose and freeze

1. Begin the discovery/interview below, then resolve the original authorized Git root, applicable CLAUDE.md/AGENTS.md and relevant index/code/verification references. Record start time, a task-derived soft target and authorized hard ceiling based on the work items and their estimates, including diagnosis, review and release; respect stricter user/project limits.
2. Use the successful hook bootstrap from this direct `/veera:fix` request, or retained actual bootstrap from this same chat. Do not ask the user for a separate start message. Use only its actual host `session_id` and configured persistent `CLAUDE_PLUGIN_DATA`; missing values block startup. Carry that actual data-directory value explicitly into CLI child environments if not inherited, with `VEERA_HOST=claude` (the default). Do not invent a global session variable, ID or environment fallback, auto-enroll other sessions or adopt legacy unbound runs. See Session isolation for separately authorized single-owner migration and actual old-owner quiescence. Require a clean committed authorized original root, then use `workspace` as shown below. Use its returned canonical TASK root, binding and owner file, never the original checkout, for task work. It creates sibling `veera-SLUG` on `veera/SLUG`; shared Git worktree/branch metadata and a narrow lock are inherent, not authority to change shared ignores/config or peers. On same-bound-task resume use `status --root TASK`; reconcile identity, contract, fingerprint, elapsed time and repairs, not fresh authorization. Never reinit to reset limits; DONE is terminal.
3. Establish expected versus observed behavior, exact reproduction/evidence, impact map and smallest plausible causal path. Separate confirmed causes from hypotheses. Inspect prerequisites cheaply; missing credentials or denial is a blocker, not a bypass opportunity.
4. Choose one bounded remedy/regression scope, including the single release version file. Resolve ordinary defaults from project evidence; ask only for material missing input or human authority. A soft target requires replanning, not abandoning diagnosis or broadening into an audit.
5. For UI defects, view actual references/design-system sources and define affected states with required rendered/browser evidence. Unavailable required visual evidence blocks that gate.
6. The coordinator owns PM responsibility throughout; delegate PM selectively. Material scope/budget decisions and soft-target replans require actual Architect impact analysis and Advisor alternatives before the PM-owned decision. Coordinator routes consultation; no invented consultation or routine committee. Reserve time for checks, review and release; do not trim required outcomes.
7. Write and read back the Bounded contract under TASK's `.veera-artifacts/`: frozen scope, observable criteria/check IDs, inspected checks argv/kind/count regex/timeouts, non-goals, UI references, repair ceiling and `release`. Release names `origin`, `main`, one supported version file and `push_authorized: true` only with user authority. Only runtime queries skip reserved UNTRACKED bookkeeping paths; tracked reserved source is rejected. Raw Git status may show bookkeeping: never hide it via shared `.git/info/exclude`/config/ignore edits or put source/tests there. Freeze expected behavior, not merely “tests green”; lock regression checks before remediation. Missing authority/repository requirements block complete delivery.
8. Run `doctor`, then init once with workspace metadata and the actual task/request/read-back contract. Pass remaining target and hard-ceiling allowances without restarting discovery time. Missing/rejected requirements are blockers; do not invent execution records.

## Remediate the same task

1. Record phase `discover`, then `plan` using `phase --root TASK --name NAME`. State causal evidence and the smallest correction. Frozen criteria and commands cannot be weakened to fit an implementation.
2. Coordinator alone routes triggered specialists. Read `context --root TASK` for the shared brief/index in existing state.json; every role gets the same run/contract/revision/current-fingerprint identity plus its role delta, criterion IDs, sources, blockers and remaining allowances. Re-read relevant stale sources. Invoke the actual `memory-steward` for compact memory updates; Read/Glob/Grep only, JSON return, no writes/delegation. Coordinator validates/saves and uses `context-import --root TASK --file PROPOSAL` under Shared TASK context (CAS, source hashes, stable IDs, 100 items/2000 characters per text). No invented identities, hashes or approvals. Checkpoint before compaction; no secrets/full logs/transcripts, parallel store, services or automatic refresh. Cache savings are unmeasured.
3. Record phase `implement`. Add focused regression tests and minimally correct the confirmed defect in the task worktree. Do not refactor adjacent systems, install dependencies or alter shared runtime without existing authority.
4. Check `status` and original elapsed time before costly work. Soft expiry sets a replanning flag, not a stop; obtain actual required consultation, record `decision --root TASK --file DECISION.json` and continue the unchanged outcome under the existing hard ceiling. No token/time shortcut may discard acceptance or evidence.

## Prove, review, publish

1. Preserve pre-fix regression failure when practical and report its absence honestly. After implementation and useful focused checks, call `release-prepare --root TASK` before final verification. It fetches authorized `origin/main`, integrates main only in TASK and idempotently patch-bumps the declared version. Preserve peers, never merge unrelated branches; resolve conflicts only within authority.
2. Record phase `verify`; run every required `check --root TASK --id ID` on the prepared tree. Preserve invocation/root, selected counts, output, exit, fingerprint and artifacts. Zero tests, static-only/synthetic/stale/missing output and unrelated success do not prove the fix. UI requires actual rendered screenshots and browser interaction evidence, not inspection alone.
3. Record phase `review`; obtain an actual independent project/plugin reviewer against frozen criteria, causal evidence, prepared source/diff and original check/UI output at the same fingerprint. No predetermined verdict or self-attestation. Authorize only its specific review JSON path under `.veera-artifacts/`, read it and import with `review --root TASK --file REVIEW.json` using actual reviewer identity.
4. Track blockers through `blocker --root TASK --file OP` (`open|attempt|result|resolve|decision`), deduplicating stable family+target. Persist distinct attempts before action and result evidence afterward; call `repair` before corrective edits. Maximum three attempts per blocker and default three global repairs, respecting lower contract/project limits and legacy explicit two; unchanged attempts are rejected. Denial/auth/human-only issues block immediately without retry. At exhaustion obtain actual Advisor+Architect consultation then a PM-owned decision: independent reprioritization or at most one bounded alternative route per TASK, never reset attempts/global repairs, override hard stops or retry the exhausted target. Resolve only with evidence; source changes require fresh checks/review. See Bounded blocker protocol.
5. Both finish and publish require no unresolved blockers and fresh verification/independent review. Call `finish --root TASK` only with all gates current; it records implementation `ready`, not DONE. Preserve one final remote push intent: no intermediate remote branches/tags, PR/status writes or manual Actions runs. Local commits are allowed and do not trigger GitHub Actions billing; one push may trigger multiple workflows/jobs, not a billing ceiling. Then `publish --root TASK` commits the exact verified tree and prefetches to confirm remote main matches the reviewed base before at most one authorized plain non-force push to `origin/main`. No force-with-lease or history overwrite; a non-fast-forward race rejects. Main checked out anywhere blocks publish BEFORE push without reading/altering that checkout. Never detach, stash, merge, reset or update-ref peers to unblock it; no unrelated branch integration.
6. A successful publish result confirms complete; a successful local finish confirms verified-local and remains unpublished. The CLI then automatically releases only this chat's binding, preserving worktree, state and evidence. Use that result as the completion receipt; do not issue another owner status/unbind command after session_binding is released. If cleanup-required is returned, resolve the cleanup issue and retry only unbind, never publication. Failed or ambiguous pushes retain their evidence and prohibit automatic retry. Original/peer checkouts and local main remain unchanged.
7. At hard expiry, user stop, denial, exhausted repairs or a genuine blocker with no eligible work, call `stop --root TASK --reason TEXT` and `checkpoint --root TASK --reason TEXT`. Report unresolved criteria, causal uncertainty and exact prerequisites. Use `resume --root TASK --file REPORT.json` only with `checkpoint_id`, actual user approval in `authorization`, `reason` and `additional_minutes` equal to the sum of authorized remaining-task estimates in `time_plan`, respecting stricter limits. Require matching fingerprint, preserve repairs/time history and never reinit. Hard expiry requires new explicit human allowance. Soft expiry alone never justifies unfinished work; its automatic replan flag is cleared by the actual consulted PM decision. No unattended continuation promise.

Return confirmed cause or remaining hypothesis, scoped correction, actual regression/check counts and exits, UI status, reviewer identity, patch version/release and push status, gaps and runtime state. A patch or implementation-ready result is not complete delivery.

## Discovery, initial questions and internal decisions

Before planning, init or source edits, read `docs/requirements-analysis.md` and `docs/intake-and-autonomy.md` under the resolved package root. For an underspecified or consequential request, use the requirements analyst process to inspect relevant code, project/domain documentation and necessary current primary sources. Resolve contradictions and turn evidence into observable requirements and an ordered plan. For a precise small change, keep analysis proportionate.

Conduct all necessary clarification during this initial discovery: offer two or three options with an evidence-based recommendation and tradeoffs; allow a custom answer. Investigate first, reuse existing answers, and follow up here if essential ambiguity remains. Never infer an answer from silence. Show the scope, acceptance and plan, then continue under existing authorization without another approval gate. Freeze validated `contract.discovery` and `contract.intake`, with no essential questions outstanding, before init.

Once implementation starts, PM, Architect and Advisor handle eligible decisions through the coordinator within captured limits. Do not restart preference interviews or ask repeated confirmations. Block only a genuinely human-only/denied/out-of-scope action, preserve its evidence and continue independent eligible work. Internal recommendations never grant native permissions or expand consent.
