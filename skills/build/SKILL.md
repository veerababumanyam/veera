# Veera — Build

Guidance package 0.1.5; explicit bootstrap and persistent ownership, untested and not installed by these files. User invocation is required because this skill has side effects. First the owner submits exactly `/veera:start` in a separate prompt; only after successful bootstrap may a separate authorized `/veera:build` task proceed. Start alone never authorizes implementation or enrollment.

## Shared rules

For an explicitly nonpublishing task, freeze `delivery_mode: "local-verify"` and omit `release` before init. In that mode the release/version requirements below do not apply: prohibit release-prepare/reconcile/publish, retain every scope/behavior/count/fingerprint/review/blocker/ownership gate, and finish to terminal `verified-local`. Report "verified locally; unpublished", preserve the binding/worktree/evidence, and never claim published complete/DONE or auto-unbind/archive. Publishing remains the default; never switch an initialized task to local mode.

Read `${CLAUDE_PLUGIN_ROOT}/docs/agent-contract.md` sections Authority and ownership, Session isolation, Bounded contract, Runtime interface, and Evidence and immutable DONE. Read UI acceptance for UI tasks, and Selective reasoning, context and repair before delegation or repair. Native/project instructions, permissions and stricter ceilings remain binding.

Own the entire approved outcome, including tests, independent review, patch version and release. Never voluntarily stop at a partial deliverable or because a soft target elapsed. Continue eligible in-scope work without routine approval pauses; report genuine blockers instead of fabricating completion. No nested loops, schedulers, recursive delegation, automatic workflows or permission bypasses.

Use medium effort only through a supported host setting; otherwise inherit the host setting. Do not force max or another model. Optimize context, not acceptance quality or reasoning at consequential decisions; return concise rationale and evidence, not chain-of-thought.

## Discover and lock

Record task start, a default 30-minute soft target and 120-minute hard ceiling, respecting stricter user/project limits and including discovery, verification and release.
2. Require successful exact `/veera:start` bootstrap from the owner's preceding standalone prompt and a separate authorized build request. Use only its actual host `session_id` and configured persistent `CLAUDE_PLUGIN_DATA`; missing values block startup. Carry that actual data-directory value explicitly into CLI child environments if not inherited, with `VEERA_HOST=claude` (the default). Do not invent a global session variable, ID or environment fallback, auto-enroll other sessions or adopt legacy unbound runs. See Session isolation for separately authorized single-owner migration and actual old-owner quiescence. Require a clean committed authorized original root, then use `workspace` as shown below. Use its returned canonical TASK root, binding and owner file, never the original checkout, for task work. It creates sibling `veera-SLUG` on `veera/SLUG`; shared Git worktree/branch metadata and a narrow lock are inherent, not authority to change shared ignores/config or peers. On same-bound-task resume use `status --root TASK`; reconcile identity, contract, fingerprint, elapsed time and repairs. Never reinit to reset limits. DONE is terminal.
3. Identify one deliverable, a targeted impact map, observable criteria, non-goals and the smallest relevant test/static commands. Include the single declared version file in scope. Resolve ordinary defaults from project evidence; ask only for necessary unresolved requirements or human-only authority. No unrelated cleanup or whole-app benchmarks.
4. For UI, view actual screenshots/mockups and design-system sources. Define rendered/browser acceptance and obtainable evidence. Missing required references or browser capability blocks that gate.
5. The coordinator owns PM responsibility on every task; separate PM delegation is selective. For material scope/budget decisions or a soft-target replan, obtain actual Architect impact analysis and Advisor alternatives before the PM-owned decision; route through the coordinator, never invent consultation. Routine sequencing needs no committee. Preserve the full outcome and reserve time for final checks/review/release.
6. Write and read back the exact Bounded contract shape under task-local `.veera-artifacts/`: frozen scope, criteria/check IDs, inspected checks argv/kind/count regex/timeouts, non-goals, UI references, repair ceiling and `release`. Release names `origin`, `main`, one supported version file and `push_authorized: true` only with actual user authority. Only runtime queries skip reserved UNTRACKED bookkeeping paths; tracked reserved source is rejected. Raw Git status may show bookkeeping: never hide it via shared `.git/info/exclude`/config/ignore edits or put source/tests there. Missing release authority or repository prerequisites is a blocker, not permission to claim a partial task complete.
7. Run `doctor`; initialize once at TASK with workspace metadata, actual request and read-back contract. Pass remaining soft-target and hard-ceiling allowances without restarting the discovery clock. Missing/rejected runtime requirements are blockers, not saved execution evidence.

## Plan and implement

1. Record `phase --root TASK --name discover`, then `plan` as appropriate. Lock the smallest plan to the frozen contract. Select project specialists only for concrete role triggers; the coordinator alone delegates under Specialist handoff and return.
2. Read `context --root TASK` for the shared brief/index in existing state.json. Give every role the same run/contract/revision/current-fingerprint identity plus its role delta, criterion IDs, source pointers, blockers and remaining allowances; re-read relevant stale sources. Invoke the actual `memory-steward` for compact memory updates; it returns JSON only with Read/Glob/Grep, no writes/delegation. Coordinator validates/saves the proposal and uses `context-import --root TASK --file PROPOSAL` under Shared TASK context (CAS, source hashes, stable IDs, 100 items/2000 characters per text). Never fabricate identities, hashes or approvals. Checkpoint before compaction; no secrets/full logs/transcripts, parallel store, services or automatic refresh. Cache savings are unmeasured.
3. Record phase `implement`. Make small architecture-consistent changes and focused tests in the owned task worktree. Preserve peer changes; record unrelated improvements as non-goals.
4. Check `status` and original elapsed time before expensive actions. A soft deadline sets a replanning flag, not a stop: obtain the required actual consultation, record `decision --root TASK --file DECISION.json` and continue toward the unchanged outcome. Never silently renew the hard ceiling or skip gates to save tokens/time.

## Verify, review, publish

1. After implementation and any useful focused checks, run `release-prepare --root TASK` before final verification. It fetches authorized `origin/main`, integrates main only in TASK and idempotently patch-bumps the declared version file. Preserve peers; do not merge unrelated branches. Conflicts or unsupported versions are blockers until safely resolved within authority.
2. Record phase `verify`; run every required `check --root TASK --id ID` on the prepared tree. Preserve invocation, selected counts, output, exit, fingerprint and artifacts. Zero tests, static-only success, stale/missing output and unrelated success are not behavioral passes. UI requires actual rendered screenshots and browser evidence under existing runtime permissions.
3. Record phase `review`; obtain an actual independent project/plugin reviewer against frozen criteria, prepared diff/source and original check/UI evidence at the same fingerprint, without an expected verdict. Authorize only its specific review JSON path under `.veera-artifacts/`, read it and import with `review --root TASK --file REVIEW.json`. Self-review cannot satisfy this gate.
4. Track blockers through `blocker --root TASK --file OP` (`open|attempt|result|resolve|decision`), deduplicating stable family+target. Persist each distinct attempt before action and result evidence afterward; call `repair` before corrective edits. Maximum three attempts per blocker and default three global repairs, respecting lower contract/project limits and legacy explicit two; unchanged attempts are rejected. Denial/auth/human-only issues block immediately without retry. At exhaustion obtain actual Advisor+Architect consultation then a PM-owned decision: independent reprioritization or at most one bounded alternative route per TASK, never reset attempts/global repairs, override hard stops or retry the exhausted target. Resolve only with evidence; source changes require fresh checks/review. See Bounded blocker protocol.
5. Both finish and publish require no unresolved blockers and fresh verification/independent review. Call `finish --root TASK` only with all gates current; it means implementation `ready`, not DONE. Call `publish --root TASK` only for the authorized exact verified tree. Preserve one final remote push intent: no intermediate remote branches/tags, PR/status writes or manual Actions runs. Local commits are allowed and do not trigger GitHub Actions billing; one push may trigger multiple workflows/jobs, not a billing ceiling. It commits that tree, prefetches to confirm remote main matches the reviewed base, then attempts at most one plain non-force push to `origin/main`; no force-with-lease or history overwrite. A non-fast-forward race rejects. Main checked out anywhere blocks publish BEFORE push without reading/altering that checkout. Never detach, stash, merge, reset or update-ref peers to unblock it; no unrelated branch integration.
6. Complete delivery means the verified task plus one confirmed remote main push, not local main synchronization. Local main refs/checkouts remain untouched even on success; the user may separately synchronize their own session. Failed/ambiguous push preserves work and attempt evidence; no automatic retry, manual substitute push or push-attempt resume. Confirm complete with `status --root TASK` before saying DONE. DONE is immutable. Owner `unbind --root TASK` uses the required flags above and only succeeds for a completed task, removing ONLY its exact own routing file. Preserve state/evidence/worktrees; no automatic archive before unbind because state is required.
7. At a hard deadline, user stop, denial, exhausted repairs or a genuine blocker with no eligible work, use `stop --root TASK --reason TEXT` and `checkpoint --root TASK --reason TEXT`; return unmet criteria, checkpoint paths and prerequisites. Resume only via `resume --root TASK --file REPORT.json` with `checkpoint_id`, actual user approval in `authorization`, `reason` and `additional_minutes` no greater than 120 or stricter limits. Require a matching fingerprint; never reset repairs/time history or reinit. Hard-deadline continuation requires new explicit human allowance. A soft target alone never justifies abandonment; its automatic replan flag is cleared by the actual consulted PM decision.

Return scope/change summary, actual checks/counts, UI status, reviewer identity, version/release and push status, gaps and runtime state. Distinguish implemented/ready from complete; never claim installation, cache savings or unrun tests.
