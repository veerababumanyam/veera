# Veera — Build

Guidance 0.3.0. Start automatically for an ordinary user request matching this skill. Read `docs/automatic-entry.md` under the installed package root and use the actual host bootstrap context. Explicit `/veera:build <task>` remains optional. Continue in the same turn without asking the user for an activation command, separate start message or routine confirmation. Automatic entry does not enroll, expand scope or authorize publication. For a new automatically routed task, freeze `delivery_mode: "local-verify"` unless the user requested publication; preserve the mode of an existing task.

## Shared rules

For an explicitly nonpublishing task, freeze `delivery_mode: "local-verify"` and omit `release` before init. In that mode the release/version requirements below do not apply: prohibit release-prepare/reconcile/publish, retain every scope/behavior/count/fingerprint/review/blocker/ownership gate, and finish to terminal `verified-local`. Report "verified locally; unpublished", preserve the worktree/evidence; successful CLI finish releases the binding automatically. Never claim published complete/DONE or automatically archive the task. Select publishing only when the user requested it; never change an initialized task to another mode.

Read `${CLAUDE_PLUGIN_ROOT}/docs/agent-contract.md` Operating core first, then sections Authority and ownership, Session isolation, Bounded contract, Runtime interface, and Evidence and immutable DONE. Read UI acceptance for UI tasks, and Selective reasoning, context and repair before delegation or repair. A spec-driven build follows the lean reading list in Spec-driven builds instead. Native/project instructions, permissions and stricter ceilings remain binding.

Own the entire approved outcome, including tests, independent review, patch version and release. Never voluntarily stop at a partial deliverable or because a soft target elapsed. Continue eligible in-scope work without routine approval pauses; report genuine blockers instead of fabricating completion. No nested loops, schedulers, recursive delegation, automatic workflows or permission bypasses.

Use medium effort only through a supported host setting; otherwise inherit the host setting. Do not force max or another model. Optimize context, not acceptance quality or reasoning at consequential decisions; return concise rationale and evidence, not chain-of-thought.

## Engineering focus

Read `${CLAUDE_PLUGIN_ROOT}/docs/engineering-standards.md` sections Applicability and authority, Role routing and Verification and evidence, then only the relevant language/UI/service/dependency sections before lock. Own typed invariants, clear boundaries and explicit failure behavior for the feature; map applicable risks to observable criteria and focused checks. Detect the repository tech stack and use its existing idioms/toolchain and trusted reuse; avoid speculative abstractions/dependencies. Apply Repository hygiene and resource ownership: inventory task-created artifacts/processes, reuse only authorized task-local caches, clean only proven-owned disposable outputs, retain verification/recovery evidence, and never manage shared caches/processes, touch other projects/global settings, delete peer/shared files or create an extra remote push for cleanup. Pass specialists section pointers and role deltas, not duplicated checklists. A spec-driven build needs only section Spec-derived tests here. Guidance is not compliance evidence or permission to expand scope.

Record task start, a task-derived soft target and authorized hard ceiling based on the work items and their estimates, respecting stricter user/project limits and including discovery, verification and release.
2. Use the successful hook bootstrap from this request, or retained actual bootstrap from this same chat; do not ask for a separate start message. Use only its actual host `session_id` and configured persistent `CLAUDE_PLUGIN_DATA`; missing values block startup. Carry that actual data-directory value explicitly into CLI child environments if not inherited, with `VEERA_HOST=claude` (the default). Never invent a global session variable, ID or environment fallback, auto-enroll other sessions or adopt legacy unbound runs; Session isolation covers separately authorized single-owner migration and actual old-owner quiescence. Require a clean committed authorized original root, then run `workspace` as below and use its returned canonical TASK root, binding and owner file, never the original checkout. It creates sibling `veera-SLUG` on `veera/SLUG`; shared Git worktree/branch metadata and a narrow lock are inherent, not authority to change shared ignores/config or peers. On same-bound-task resume use `status --root TASK`; reconcile identity, contract, fingerprint, elapsed time and repairs. Never reinit to reset limits. DONE is terminal.
3. Freeze one deliverable, a targeted impact map, observable criteria, non-goals and the smallest relevant checks (Delivery craft). Include the single declared version file in scope when publishing. Resolve ordinary defaults from project evidence; ask only for necessary unresolved requirements or human-only authority. No unrelated cleanup or whole-app benchmarks.
4. For UI, view actual screenshots/mockups and design-system sources. Define rendered/browser acceptance and obtainable evidence. Missing required references or browser capability blocks that gate.
5. The coordinator owns PM responsibility on every task; separate PM delegation is selective. For material scope/budget decisions or a soft-target replan, obtain actual Architect impact analysis and Advisor alternatives before the PM-owned decision; route through the coordinator, never invent consultation. Routine sequencing needs no committee. Preserve the full outcome and reserve time for final checks/review/release.
6. Write and read back the exact Bounded contract shape under task-local `.veera-artifacts/`: frozen scope, criteria/check IDs, inspected checks argv/kind/count regex/timeouts, non-goals, UI references, repair ceiling, `contract.discovery`, `contract.intake` and `release` (publishing only). Release names `origin`, `main`, one supported version file and `push_authorized: true` only with actual user authority. Only runtime queries skip reserved UNTRACKED bookkeeping paths; tracked reserved source is rejected. Raw Git status may show bookkeeping: never hide it via shared `.git/info/exclude`/config/ignore edits or put source/tests there. Missing release authority or repository prerequisites is a blocker, not permission to claim a partial task complete.
7. Run `doctor`; initialize once at TASK with workspace metadata, actual request and read-back contract. Pass remaining soft-target and hard-ceiling allowances without restarting the discovery clock. An exit-2 refusal names the prerequisite: fix that one field, never resubmit unchanged. Missing/rejected runtime requirements are blockers, not saved execution evidence.

Only the coordinator owner runs the CLI. Required forms (quote actual values; placeholders are not IDs or environment variables):

Hook and CLI must use the same actual persistent directory and host namespace. ## Delivery craft

- **Requirements.** A written spec or detailed request is the requirement source: extract every normative rule (routes, fields, limits, status codes, error titles, ordering, invariants, concurrency, persistence) with its exact values and a section pointer, plus every existing behavior it declares binding. Group them into at most 30 requirements, one criterion per observable behavior cluster. When the spec and code answer everything, ask zero questions and record the gaps you fill as assumptions; do not stage an approaches menu or design-approval round.
- **Checks.** Give each criterion group a focused `test` check and freeze the project's existing suite as the regression check when preserved behavior is binding. The recorded count is the sum of every regex match, so match only the runner's single total line and pin the reporter in argv (for example `node --test --test-reporter=tap` with `(?m)^# tests (\d+)`). A check fails if it creates or changes any repository file except an ignored one outside scope, and ignored files inside scope block finish, so tests write data and temp files under the OS temp directory. Use finite timeouts; add a startup/smoke check when the spec requires the program to run.
- **Plan.** Order vertical slices so each ends testable. Each slice names files, the interfaces later slices consume, the spec values verbatim and its tests. Add a Review focus of at most five inputs or failure modes the spec implies but does not test (races, boundaries, malformed input, restart, cross-tenant access), each pinned by a test in the owning slice. A plan step decides something; "handle edge cases" decides nothing.
- **Execute.** Per slice: write the test, run it and watch it fail for the intended reason, write the minimal code, run it green, move on. Implement-phase runs are feedback only; recorded checks are the evidence. Send long output to a `.veera-artifacts/` file and read its tail. Read source by the impact map, not whole trees. Settle what the spec leaves open yourself, note each ruling with its reason and cost if wrong, and report the list at the end.
- **Before verify**, map every criterion and Review focus line to named passing tests and remove stubs/TODOs. After review, re-grade each finding by its effect on a user: Critical/Important ones go through the blocker protocol and `repair`, each with a test that fails first, then fresh checks and a fresh review; Minor ones are reported as deferred, never silent scope growth.

## Plan and implement

1. Record `phase --root TASK --name discover`, then `plan` as appropriate; phases move one step at a time. Lock the smallest plan to the frozen contract. Select project specialists only for concrete role triggers; the coordinator alone delegates under Specialist handoff and return, passing file paths and criterion IDs instead of pasted history.
2. Read `context --root TASK` for the shared brief/index in existing state.json. Give every role the same run/contract/revision/current-fingerprint identity plus its role delta, criterion IDs, source pointers, blockers and remaining allowances; re-read relevant stale sources. Invoke the actual `memory-steward` for compact memory updates; it returns JSON only with Read/Glob/Grep, no writes/delegation. Coordinator validates/saves the proposal and uses `context-import --root TASK --file PROPOSAL` under Shared TASK context (CAS, source hashes, stable IDs, 100 items/2000 characters per text). Never fabricate identities, hashes or approvals. Checkpoint before compaction; no secrets/full logs/transcripts, parallel store, services or automatic refresh. Cache savings are unmeasured.
3. Record phase `implement`. Make small architecture-consistent changes and focused tests in the owned task worktree. Preserve peer changes; record unrelated improvements as non-goals. When the request names a written specification, follow Spec-driven builds below for tests.
4. Check `status` and original elapsed time before expensive actions. A soft deadline sets a replanning flag, not a stop: obtain the required actual consultation, record `decision --root TASK --file DECISION.json` and continue toward the unchanged outcome. Never silently renew the hard ceiling or skip gates to save tokens/time.

## Spec-driven builds

When the request names a written specification (a spec file, numbered invariants, an error table or acceptance list), read `${CLAUDE_PLUGIN_ROOT}/docs/engineering-standards.md` section Spec-derived tests before writing tests. The specification is the requirements analysis and the test oracle: no interview for what it states, and read it and the code it touches once. Lean reading list: this skill plus that one section is everything a spec-driven build reads; skip agent-contract.md, requirements-analysis.md, intake-and-autonomy.md, model-routing.md, dashboard.md and automatic-entry.md, and never grep runtime sources for formats, unless a blocker, UI, publication, a new dependency or delegation beyond the single reviewer arises. Every tool call re-sends the whole context, so tokens and wall-clock scale with calls times context: batch independent commands into one call and never re-read a file you already have.

1. Before tests, write the criterion ledger: every numbered invariant and every concurrency, idempotency, pagination, persistence and audit rule under its spec ID. Each ID maps to a named test and becomes a contract criterion; an unmapped ID is an open gap.
2. Assert exact spec observables at boundaries, transitions, refused actors, unchanged-on-failure state and real parallel bursts, through the public interface and existing helpers only. Never pin behavior the specification leaves open or use hooks, clocks or modules the change added.
3. Before review, run the mutation probe on the riskiest IDs (temporary edit, run only the new test file, revert and confirm the diff) and re-read every assertion against its clause. Sharpen tests that let a mutant survive.
4. Iterate on the new test file alone. Run the full suite once before review and once on the final tree; never rerun an unchanged suite for confidence. The frozen `check` is that pre-review run, and when review changes nothing it is also the final-tree run. Give the single independent reviewer the ledger with the diff. After review change code or tests only for a spec-backed defect; a hedge for a silent clause gets no new pinning test.
5. Setup in three calls: one Bash for `doctor` plus `workspace`; one Bash that prints the spec and every source/test file the change touches and runs the baseline suite (take `count_pattern` from its summary line); then write the contract with no discovery or intake block, since the ledger is the brief. One `test` check, the project's full suite including the new file, serves every criterion; criteria are the ledger IDs. Example for a node:test suite: `{"delivery_mode": "local-verify", "scope": ["src/", "tests/", "README.md"], "criteria": [{"id": "C1", "text": "C1 clause -> test names", "checks": ["suite"]}], "checks": [{"id": "suite", "argv": ["node", "tests/run.js"], "kind": "test", "count_pattern": "(?m)^(?:#|\u2139) pass (\\d+)\\s*$", "timeout_seconds": 600}], "non_goals": ["unchanged spec files"], "max_repairs": 3}`. Keep the contract file ASCII: write a non-ASCII summary marker as a `\uXXXX` escape, since a shell or editor may re-encode it and leave a pattern that reads nothing.
6. One Bash runs `init`, `phase --name plan` and `phase --name implement` (phases are strictly ordered); start `dashboard` once with run_in_background and get its URL from one `dashboard-info` chained into a later CLI call, never by polling or reading its output file. Bound sessions: write files with Write/Edit, diffs with `git diff --output=PATH`, no shell redirects or deletes; leave probe backups under `.veera-artifacts/`. Every refused call is a wasted turn.
7. Run the mutation probe as one scripted Bash pass over all chosen mutants (copy, edit, run the new test file, restore, print killed/survived, end with `git diff --stat`). Finish README/docs edits before verify: any edit after `check` changes the fingerprint and forces a new check and review. Skip a separate smoke run unless the suite cannot reach the entry point the spec names.
8. One Bash runs `phase --name verify`, `check --id suite`, `phase --name review` and `git diff --output=.veera-artifacts/diff.patch`. The single reviewer gets one compact prompt: spec path, ledger, diff path plus the untracked new files (the diff omits them), check log/count/fingerprint, criterion IDs, and the review file shape `{"reviewer", "approved", "criteria": [every ID], "fingerprint", "notes"}`; it reports only spec-backed defects, does not rerun the full suite and replies in under 150 words. Print that small file, import it and finish in one Bash, adding the commit there when one is wanted. A `check` result with `defective_check` (exit 0, zero tests counted) whose log shows the suite ran is a misread summary line, not a failing suite: write `{"checks": [{"id": "suite", "count_pattern": PATTERN}]}` with a pattern that reads that line, run `correct-contract --root TASK --reason EVIDENCE --file FILE`, then `check` again. The controller accepts it only if the new pattern counts tests in the failed run's own log; it spends no repair, needs no approval and never stops the run, and no other field of the check may change. Expect at most one repair round: one `repair`, one fix, one `check`, one re-review of the changed hunks; a note without a spec-backed defect goes in `notes`, not into another loop.

## Verify, review, publish

1. Publishing only: while still in `implement`, run `release-prepare --root TASK` before final verification. It fetches authorized `origin/main`, integrates main only in TASK and idempotently patch-bumps the declared version file. Preserve peers; do not merge unrelated branches. Conflicts or unsupported versions are blockers until safely resolved within authority.
2. Record phase `verify`; run every required `check --root TASK --id ID` once on the final tree. Preserve invocation, selected counts, output, exit, fingerprint and artifacts. Zero tests, static-only success, stale/missing output and unrelated success are not behavioral passes. An unchanged failure needs a diagnosis, not a rerun. UI requires actual rendered screenshots and browser evidence under existing runtime permissions.
3. Record phase `review`; obtain an actual independent project/plugin reviewer against frozen criteria, the request/spec, Review focus, prepared diff/source and original check/UI evidence at the `fingerprint --root TASK` value, without an expected verdict or "do not flag" steering. Authorize only its specific review JSON path under `.veera-artifacts/`, read it and import with `review --root TASK --file REVIEW.json`. Self-review cannot satisfy this gate.
4. Track blockers through `blocker --root TASK --file OP` (`open|attempt|result|reconcile|resolve|decision`), deduplicating stable family+target. Persist each distinct attempt before action and result evidence afterward; call `repair --root TASK --reason TEXT` with a new reason before corrective edits (it returns to `implement` and clears review). Maximum three attempts per blocker and default three global repairs, respecting lower contract/project limits and legacy explicit two; unchanged attempts are rejected. Denial/auth/human-only issues block immediately without retry. At exhaustion obtain actual Advisor+Architect consultation then a PM-owned decision: independent reprioritization or at most one bounded alternative route per TASK, never reset attempts/global repairs, override hard stops or retry the exhausted target. Resolve only with evidence; source changes require fresh checks/review. See Bounded blocker protocol.
5. Both finish and publish require no unresolved blockers and fresh verification/independent review. Call `finish --root TASK` only with all gates current; in publishing mode it means implementation `ready`, not DONE. Call `publish --root TASK` only for the authorized exact verified tree, under Evidence and immutable DONE: one final remote push intent (no intermediate remote branches/tags, PR/status writes or manual Actions runs), at most one plain non-force push to `origin/main` after the prefetch matches the reviewed base, no force-with-lease or history overwrite. Main checked out anywhere blocks publish BEFORE push without reading/altering that checkout. Never detach, stash, merge, reset or update-ref peers to unblock it; no unrelated branch integration.
6. A successful publish result confirms complete; a successful local finish confirms verified-local and remains unpublished. Either automatically releases only this chat's binding, preserving worktree, state and evidence; that result is the completion receipt, so issue no further owner status/unbind command after session_binding is released. If cleanup-required is returned, resolve the cleanup issue and retry only unbind, never publication. Failed or ambiguous pushes retain their evidence and prohibit automatic retry. Original/peer checkouts and local main remain unchanged.
7. At a hard deadline, user stop, denial, exhausted repairs or a genuine blocker with no eligible work, use `stop --root TASK --reason TEXT` and `checkpoint --root TASK --reason TEXT`; return unmet criteria, checkpoint paths and prerequisites. Resume only via `resume --root TASK --file REPORT.json` with `checkpoint_id`, actual user approval in `authorization`, `reason` and `additional_minutes` equal to the sum of authorized remaining-task estimates in `time_plan`, respecting stricter limits. Require a matching fingerprint; never reset repairs/time history or reinit. Hard-deadline continuation requires new explicit human allowance. A soft target alone never justifies abandonment; its automatic replan flag is cleared by the actual consulted PM decision.

Return scope/change summary, actual checks/counts, UI status, reviewer identity, rulings made, deferred findings, version/release and push status, gaps and runtime state. Distinguish implemented/ready from complete; never claim installation, cache savings or unrun tests.

## Discovery, initial questions and internal decisions

Before planning, init or source edits, read `docs/requirements-analysis.md` and `docs/intake-and-autonomy.md` under the resolved package root, except for a spec-driven build, whose specification and criterion ledger are the analysis. For an underspecified or consequential request, use the requirements analyst process to inspect relevant code, project/domain documentation and necessary current primary sources. Resolve contradictions and turn evidence into observable requirements and an ordered plan. For a precise small change, keep analysis proportionate.

Conduct all necessary clarification during this initial discovery: offer two or three options with an evidence-based recommendation and tradeoffs; allow a custom answer. Investigate first, reuse existing answers, and follow up here if essential ambiguity remains. Never infer an answer from silence. Show the scope, acceptance and plan, then continue under existing authorization without another approval gate. Freeze validated `contract.discovery` and `contract.intake`, with no essential questions outstanding, before init; a spec-driven build omits both and freezes its ledger as the criteria.

Once implementation starts, PM, Architect and Advisor handle eligible decisions through the coordinator within captured limits. Do not restart preference interviews or ask repeated confirmations. Block only a genuinely human-only/denied/out-of-scope action, preserve its evidence and continue independent eligible work. Internal recommendations never grant native permissions or expand consent.

## Automatic live dashboard

Immediately after successful init and before the first implementation edit, follow `docs/dashboard.md` (a spec-driven build uses step 6 of Spec-driven builds instead): launch the owned `dashboard --root TASK --port 0` command in a host-tracked background process. It opens the browser automatically and saves the live address. Capture its output/process handle and show the user the clickable live URL once at the beginning. Do not wait for a dashboard request or ask again for permission to open this routine local preview. Reuse an existing task server; do not duplicate it. It is not a scheduler or gate. If the user asks for the dashboard or its path later, use `dashboard-info` and provide the validated URL and absolute record path. Report only an actual returned URL/port or blocker; a browser launch failure falls back to the link while eligible work continues.
